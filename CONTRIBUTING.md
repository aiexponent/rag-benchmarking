# Contributing to RAG Benchmarking

Thank you for your interest in contributing to **RAG Benchmarking**! We build open-source, framework-agnostic evaluation tooling for retrieval-augmented generation (RAG) and agentic AI systems, providing deterministic evidence for EU AI Act Article 15 (accuracy, robustness, and cybersecurity).

All AiExponent tools are distributed under the **Apache License 2.0**. We welcome contributions from software engineers, AI researchers, compliance officers, and legal technologists.

---

## ⚡ 10-Minute Low-Code Contribution Track: Evaluation Datasets

You can make an immediate, high-impact contribution **without writing Python code** by adding domain-specific evaluation pairs to our golden datasets in [`data/golden/qa.jsonl`](data/golden/qa.jsonl).

Each line is a JSON object with question, ground truth, and reference contexts:

```json
{
  "question": "What documentation must high-risk AI system deployers maintain under Article 26 of the EU AI Act?",
  "ground_truth": "Deployers must keep logs generated by high-risk AI systems under their control for at least six months where appropriate under applicable law.",
  "contexts": [
    "Article 26(5) requires deployers of high-risk AI systems to keep system logs for at least six months, unless other Union or national law requires longer retention."
  ]
}
```

To contribute:
1. Fork the repository and create a branch: `git checkout -b data/add-article-26-golden-eval`
2. Add your verified Q&A pairs to `data/golden/qa.jsonl`.
3. Submit a Pull Request describing your domain source.

## 🛠️ Local Development Setup

### Prerequisites
- Python 3.11 or 3.12
- Git

### Initial Setup
```bash
# 1. Clone your fork
git clone https://github.com/<your-username>/rag-benchmarking.git
cd rag-benchmarking

# 2. Create and activate a virtual environment
python3 -m venv .venv
source .venv/bin/activate   # On Windows: .venv\Scripts\activate

# 3. Upgrade pip and install development dependencies
pip install --upgrade pip
pip install -e ".[test,lint]"

# 4. (Optional) Set up local environment variables for LLM APIs
cp .env.example .env
```

## 🧪 Quality Gates & Local Verification

Before submitting a Pull Request, ensure all local quality gates pass cleanly. Our CI enforces zero tolerance for linting, typing, or test failures.

### 1. Code Formatting & Linting
We use **Ruff** for high-speed linting and formatting:
```bash
# Check code style and common bugs
python -m ruff check src tests

# Auto-fix lint violations where possible
python -m ruff check --fix src tests

# Check formatting compliance (120-char line limit)
python -m ruff format --check src tests

# Reformat code
python -m ruff format src tests
```

### 2. Static Type Checking
We strictly enforce **mypy** with zero suppression:
```bash
python -m mypy src
```

### 3. Automated Test Suite
Run the full test suite with **pytest**:
```bash
# Run the complete test suite
python -m pytest -v

# Run by test suite layer
python -m pytest tests/unit/ -v
python -m pytest tests/integration/ -v
python -m pytest tests/e2e/ -v
```

### 4. License Compliance
We dogfood AiExponent's **License Compliance Checker (LCC)**:
```bash
lcc scan --policy permissive --exclude ".venv/**" --exclude "venv/**"
```

## 🌿 Git & Pull Request Workflow

### 1. Branch Naming
Create focused, single-purpose branches from `main`:
- `feat/<feature-name>` (e.g., `feat/add-reciprocal-rank-fusion`)
- `fix/<bug-name>` (e.g., `fix/qdrant-connection-pool-timeout`)
- `docs/<doc-topic>` (e.g., `docs/update-installation-guide`)
- `chore/<task>` (e.g., `chore/bump-ragas-dependency`)

### 2. Commit Message Standards
We follow the [Conventional Commits](https://www.conventionalcommits.org/) specification:
- `feat:` new evaluation metric, retrieval integration, or CLI command
- `fix:` bug fix or typing correction
- `docs:` documentation, README, or dataset enhancements
- `test:` new unit, integration, or e2e test cases
- `chore:` dependency updates, packaging, or CI workflow changes

*Example*: `feat(eval): add multi-turn agent trajectory evaluation runner`

### 3. Pull Request Checklist
Before opening a PR, ensure:
- [ ] Code adheres to PEP 8 / Ruff style rules and passes `python -m ruff format --check src tests`.
- [ ] All new functions and public APIs carry type annotations and docstrings.
- [ ] `python -m mypy src` reports 0 issues.
- [ ] All unit, integration, and e2e tests pass via `pytest`.
- [ ] New features include corresponding automated tests under `tests/unit/`, `tests/integration/`, or `tests/e2e/`.
- [ ] PR description details the changes, rationale, and verification output.
